# Confirmed findings (severity-ordered)

## 1. [CRITICAL] `src/bobe/openai_realtime.py:295` — Unretried session exceptions escape start_up and tear down the whole audio stack

**What:** start_up() only retries `except (ConnectionClosedError, RealtimeSessionError)`. The session task can terminate with other exception types that propagate out of start_up, through `asyncio.gather(*self._tasks)` at src/bobe/console.py:135, ending runner() and thus the entire app (main.run's finally tears down movement/media/robot). Verified raisers: (a) the installed openai SDK's `AsyncRealtimeConnection.send()` enqueues any payload whose `ws.send` failed into an internal `_send_queue` and re-raises (site-packages openai/resources/realtime/realtime.py:352-357); when the session iterator later hits `ConnectionClosedError`, `__aiter__` sees the non-empty queue and raises `WebSocketConnectionClosedError` (an OpenAIError, realtime.py:315-323) — NOT ConnectionClosedError, since the app passes no `on_reconnecting` so SDK auto-reconnect is disabled (`make_ws=None`, realtime.py:665). (b) `client.realtime.connect()` raising OSError/socket.gaierror/TimeoutError on DNS/network failure during a retry attempt. (c) SystemExit from prompts.get_realtime_session_instructions() (sys.exit) called at line 687 — `except Exception` at 720 does not catch BaseException.

**Failure scenario:** Robot is awake and streaming mic audio. Wi-Fi blips and the websocket drops abnormally (1006). receive() sends a mic frame -> `input_audio_buffer.append` raises ConnectionClosedError; the SDK enqueues that unsent frame internally and receive() handles the error. Moments later the session task's `async for` hits ConnectionClosedError, finds the poisoned send queue, and raises WebSocketConnectionClosedError. start_up's except tuple does not match -> exception propagates to asyncio.gather in console.py:135 -> runner exits -> asyncio.run cancels record/play loops -> main.run finally shuts down MovementManager, media, and disconnects the robot. The entire app dies from a single network hiccup; user finds the robot completely dead until manual restart. Because a failed app-level send while awake is the COMMON path preceding session-task failure, the 3-attempt retry loop is routinely bypassed.

**Suggested fix:** Broaden the retry to `except asyncio.CancelledError: raise` plus `except Exception as e:` (log and retry with backoff), and separately guard against SystemExit around the instructions loader inside _run_realtime_session. At minimum add `WebSocketConnectionClosedError` (openai) and `OSError`/`TimeoutError` to the retried tuple.

## 2. [CRITICAL] `src/bobe/openai_realtime.py:316` — start_up finally/retry races _restart_session: clobbers healthy connections and spawns dual concurrent sessions

**What:** start_up() awaits the task T1 it created at line 288-292; its per-attempt `finally` (316-319) unconditionally sets `self.connection = None` and clears `_connected_event`. Meanwhile receive()'s send-failure path (1124-1127) calls `_restart_session()`, which after T1 dies creates a NEW task T2 (line 398) and overwrites `self._realtime_session_task`. When T1's exception resumes start_up on the same loop, the finally nukes T2's freshly-established connection/_connected_event, and the retry loop then creates T3 via create_task (288) while T2 is still running its `async for`. Two `_run_realtime_session` instances now run concurrently: both write `self.connection` (last-writer-wins), both call `tool_manager.start_up` (which overwrites `_lifecycle_tasks` without cancelling, background_tool_manager.py:277), and whichever dies first runs `await self.tool_manager.shutdown()` in its finally (line 921), cancelling the OTHER session's listener/cleanup tasks. Even in the clean-close ordering (our own conn.close() -> ConnectionClosedOK -> T1 exits 'normally' -> start_up returns at 293-294), the finally still wipes the connection T2 just established, then receive() sees connection=None, waits the 2s throttle, calls _restart_session again, which times out on the cleared event and cancels the healthy T2 (390-394).

**Failure scenario:** One transient websocket drop while awake -> receive() triggers _restart_session (T2 connects) -> start_up's finally wipes connection/_connected_event -> either a third session task is spawned alongside T2 (duplicate event dispatch: doubled assistant audio in output_queue, transcripts handled twice, duplicate tool calls, _response_done_event handshake corrupted, tool results never delivered after the cross-shutdown at line 921), or the healthy T2 is judged stalled and cancelled ~7s after connecting, producing minutes of connect/drop churn. User experiences exactly 'constant small errors': overlapping/doubled speech, tools that never answer, and repeated dead air after any network blip.

**Suggested fix:** Make one owner of the session lifecycle: have start_up loop on a supervisor that always awaits `self._realtime_session_task` (whatever it currently is) instead of the task object it created, and remove the connection-clearing finally from start_up (move cleanup into _run_realtime_session's own finally). Guard _restart_session and start_up with an asyncio.Lock so only one session task can ever exist.

## 3. [HIGH] `src/bobe/wake_daemon/engine.py:237` — Partial-transcribe throttle uses pre-transcribe timestamp; once transcribe >= 0.45s every buffered chunk re-transcribes the whole utterance

**What:** In WhisperWakeSession.feed (engine.py:230-237), `now = time.monotonic()` is captured, the throttle check `now - self._last_partial_at >= PARTIAL_TRANSCRIBE_INTERVAL_S` (0.45s) passes, a blocking full-utterance transcribe runs (`self.engine.transcribe(np.concatenate(self._speech_samples), ...)`), and then `self._last_partial_at = now` stores the PRE-transcribe timestamp. The WS handler (server.py:199) processes frames strictly sequentially via `await asyncio.to_thread(session.feed, pcm)`, so while a transcribe runs, incoming ~30ms PCM frames pile up in uvicorn's receive buffer. When feed returns after D seconds, the very next buffered chunk sees elapsed == D; whenever D >= 0.45s the throttle is permanently defeated for the rest of the utterance and EVERY buffered chunk triggers another full re-transcription of the growing utterance (up to max_utterance_s=3.0s plus trailing silence). D >= 0.45s is guaranteed on the first transcribe after daemon start (lazy model load inside transcribe, engine.py:50/66-85, seconds to minutes if the model must download) and is plausible on warm runs with 2-3s utterances. A 3s utterance at 30ms frames yields ~100 chunks x D each — tens of seconds of serialized processing for 3s of audio, during which wake/sleep events, `listen` mode switches, and stats are all queued behind the backlog.

**Failure scenario:** Daemon restarts (or model is cold). User says 'hey bobe, what's the weather'. First partial transcribe blocks loading Whisper (5-30s); ~50 frames buffer up. When it finishes, each buffered frame re-transcribes the full utterance (each 0.2-0.6s warm), adding another 10-30s. The wake event reaches the robot 15-60s late — user thinks the robot ignored them, repeats the phrase, walks away, then the robot chimes and wakes 'randomly' later. Same mechanism delays sleep-phrase detection while awake ('go to sleep' seemingly ignored, robot goes to sleep much later). Intermittent because it depends on cold model / utterance length / machine load — exactly the 'small errors here and there' pattern.

**Suggested fix:** Set the throttle timestamp AFTER the transcribe completes (`self._last_partial_at = time.monotonic()` post-call) so the interval measures wall time since the last transcribe finished; additionally preload the model at daemon startup (call engine._load_model() in create_app or a startup event) and consider windowing partials to the last ~2s of audio instead of the full utterance.

## 4. [HIGH] `src/bobe/tools/background_tool_manager.py:268` — Tool-notification listener task dies permanently on any callback exception

**What:** `_listener()` (lines 265-269) awaits `callback(bg_tool)` with no try/except. The only callback, `OpenaiRealtimeHandler._handle_tool_result`, catches ONLY `ConnectionClosedError` (openai_realtime.py:576). `websockets.ConnectionClosedOK` is a sibling class, not a subclass (verified websockets/exceptions.py:146-156), and is raised when `conversation.item.create` is sent on a connection that was closed cleanly (e.g. the stale conn left behind by finding #4, closed by our own `conn.close()` with code 1000). The exception kills the `bg-tool-listener-callback` task silently. Worse: the exception is stored in the task; at session end, `shutdown()` (291-297) does `task.cancel(); await task` catching only CancelledError, so the stored ConnectionClosedOK re-raises out of `tool_manager.shutdown()` inside `_run_realtime_session`'s finally (openai_realtime.py:921), replacing a retryable session exception with one that start_up does not retry (finding #1) — cascading to full app teardown.

**Failure scenario:** A slow tool (e.g. ask_claude, 5-15s) is running when the realtime session is restarted; `self.connection` still points at the cleanly-closed old socket (or is repointed mid-callback). The tool completes, _handle_tool_result passes the `if not self.connection` check, `conversation.item.create` raises ConnectionClosedOK, listener task dies. Every subsequent tool call in the session runs to completion but its function_call_output is never delivered: the model says 'let me check that' and then hangs forever — user hears silence and must re-ask. On the next session teardown, the dead task's exception resurfaces from shutdown() and can kill the whole app via finding #1.

**Suggested fix:** Wrap the callback invocation in `try/except Exception: logger.exception(...)` inside _listener so one bad notification cannot kill delivery; in _handle_tool_result catch `websockets.exceptions.ConnectionClosed` (the common base) or plain Exception; in shutdown() use `await task` inside `except (asyncio.CancelledError, Exception)`.

## 5. [HIGH] `src/bobe/openai_realtime.py:911` — _run_realtime_session finally never clears self.connection/_connected_event -> stale 'connected' state after graceful close

**What:** The finally block at lines 911-921 cancels the response sender and shuts down the tool manager but never resets `self.connection = None` / `self._connected_event.clear()`. The openai SDK's `__aiter__` swallows ConnectionClosedOK and ends iteration normally (verified site-packages openai/resources/realtime/realtime.py:313-314), so a server-initiated clean close (OpenAI realtime sessions have a hard max duration; idle closes) ends the async-for without an exception. For a restart-spawned task (name 'openai-realtime-restart', NOT awaited by start_up — start_up's finally only covers the task it awaited), nothing clears the handler state: `self.connection` keeps pointing at a dead connection and `_connected_event` stays set. `_ensure_openai_connection` (323-324) then returns True instantly against a corpse. Related: the ConnectionClosedError path in _handle_tool_result (578-579) sets connection=None but does not clear _connected_event either.

**Failure scenario:** Robot is asleep; the current session was created by _restart_session earlier; after ~30-60 min OpenAI closes the websocket cleanly. Session task exits; handler still 'connected'. User says 'hey bobe, what's the weather' -> _transition_to_awake -> _ensure_openai_connection returns True immediately -> chime plays, pre-wake audio flush fails silently ('Could not flush pre-wake audio' at warning level, line 1015) -> the user's question audio is sent via receive(), the append raises, connection is dropped, and reconnect is throttled 2s (1103) before _restart_session. Net effect: robot chimes as if awake, then completely ignores the first utterance(s). Intermittent 'it hears the wake word but doesn't answer'.

**Suggested fix:** In _run_realtime_session's finally, add `if self.connection is conn: self.connection = None; self._connected_event.clear()`. Also clear _connected_event at line 579.

## 6. [HIGH] `src/bobe/tools/background_tool_manager.py:291` — shutdown() cancels listener before tools; cancelled-tool notifications survive in the persistent queue and replay into the next session

**What:** shutdown() cancels and awaits `_lifecycle_tasks` (listener) FIRST (291-298), then cancels running tools WITHOUT awaiting them (300-301). A cancelled bg tool task doesn't die: `_dispatch_tool_call` swallows CancelledError and returns `{"error": "Tool cancelled"}` (core_tools.py:312-314) — itself asyncio misuse, as it converts task cancellation into normal completion — so `_run_tool` continues and puts a notification into `_notification_queue` (line 190). That queue is a manager instance field created once (line 100) and persists across realtime session restarts (the manager lives on the handler; start_up is re-run per session at openai_realtime.py:733). The next session's fresh listener immediately drains the stale notifications and _handle_tool_result posts `function_call_output` with call_ids belonging to the DEAD session's conversation.

**Failure scenario:** A dance/ask_claude tool is running when the websocket drops. Session finally -> tool_manager.shutdown(): listener cancelled, tool cancelled, 'Tool cancelled' notification enqueued into the surviving queue. Reconnect succeeds; new listener starts and instantly sends function_call_output for a call_id the new conversation has never seen -> OpenAI replies with an `error` event -> line 908-910 puts '[error] ...' into output_queue and the robot may speak an error right after reconnecting, plus a spurious response.create (line 563) makes it talk unprompted. This is a direct producer of the reported random '[error]' utterances and unprompted speech after reconnects.

**Suggested fix:** In shutdown(): cancel and await the running tool tasks FIRST, then cancel the listener; drain `_notification_queue` (get_nowait loop) at the end of shutdown or at the start of start_up(). In core_tools._dispatch_tool_call, re-raise CancelledError instead of returning a result.

## 7. [HIGH] `src/bobe/openai_realtime.py:398` — Reconnect race stacks two concurrent realtime sessions; loser websocket becomes unclosable

**What:** There are two uncoordinated creators of `_realtime_session_task`: `start_up()`'s retry loop (openai_realtime.py:288-291, backoff sleep at 304 happens BEFORE the per-attempt `finally` at 316-319) and `_restart_session()` (openai_realtime.py:398-401, reached from `receive()`'s send-failure path at 1127 and from `_ensure_openai_connection` at 337). Neither checks whether the other just created a task: `_restart_session` only skips creation when the CURRENT `_realtime_session_task` is not done (388), and `start_up` unconditionally creates a fresh task on its next attempt, overwriting `self._realtime_session_task` and losing the only reference the shutdown/invalidate paths use. Worse, `start_up`'s per-attempt `finally` (316-319) sets `self.connection = None` and clears `_connected_event` even when a restart-spawned task has just registered a healthy connection (727-728), orphaning that live websocket. `handler.shutdown()` (1142-1149) and `_invalidate_realtime_connection()` (363-373) can only cancel/close the newest task/connection, so the overwritten session's OpenAI realtime websocket stays open (and billed) until the server drops it, while its event loop keeps running and its `finally` later interferes with the live session (see the BackgroundToolManager finding).

**Failure scenario:** Mid-conversation the OpenAI websocket drops. (1) Session task T1 raises ConnectionClosedError; start_up catches it at 295 and sleeps its 1-1.5s backoff (connection attr still stale — finally hasn't run yet). (2) The next mic frame in receive() fails to send (1113), sets connection=None and calls _restart_session (1127); since T1 is done, a new task 'openai-realtime-restart' is created at 398 and connects (~0.5s), setting self.connection and _connected_event. (3) start_up wakes from backoff, `continue` triggers the finally (316-319) which nukes the restart task's healthy connection/_connected_event, then attempt 2 creates ANOTHER task at 288, overwriting _realtime_session_task — the restart task reference is lost. (4) Two `_run_realtime_session` coroutines now hold two open OpenAI websockets; the orphaned one can never be closed by shutdown()/_invalidate and lingers until the server closes it (up to the realtime session cap), and every subsequent network blip repeats the race — the classic works-at-first, degrades-over-hours pattern the owner reports, plus doubled session cost.

**Suggested fix:** Make session-task creation single-owner: e.g., have start_up own the reconnect loop and turn _restart_session into a signal (asyncio.Event) that start_up consumes; or guard both creation sites with an asyncio.Lock and re-check `self._realtime_session_task is not None and not done()` before creating. In start_up's finally, only clear self.connection/_connected_event if the task that just finished is still `self._realtime_session_task` (i.e., no restart superseded it).

## 12. [HIGH] `src/bobe/profiles/_bobe_locked_profile/sweep_look.py:48` — sweep_look head rotates the wrong way (slerp >180° wrap) and counter-rotates against the lerped body yaw when started off-center

**What:** Move 1 (`move_to_left`, sweep_look.py:48) targets an ABSOLUTE world head yaw of +0.9*pi (162°, line 42/47) from the arbitrary current head pose, while GotoQueueMove interpolates the head via linear_pose_interpolation (dance_emotion_moves.py:118), which uses scipy's as_rotvec — the MINIMAL rotation, always <=180°. If the current head world yaw is below -18°, the required relative rotation exceeds 180°, so slerp rotates the head the SHORT way (negative/clockwise) while body_yaw is lerped linearly the intended way (+162°, dance_emotion_moves.py:130). I reproduced this with the repo venv: starting head yaw -40° -> at t=0.5 head world yaw = -119° while body yaw = +81°, a head-vs-body demand of ~200°, physically impossible for the Stewart platform. The comment at line 69 shows the pi-boundary was only considered for the return leg, not for move 1's arbitrary start. **Suggested fix:** Build the sweep relative to the current pose: compute target head poses by composing the current pose with bounded relative yaw steps (each <=~90°), or first queue a goto back to center (like move 3) before sweeping; also derive the head yaw target from current_body_yaw (target head yaw = current_body_yaw + max_angle) so head and body targets stay in lockstep, and split any leg whose relative rotation could exceed 180° into intermediate waypoints.
